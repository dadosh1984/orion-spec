# Spec: zero_dep_runtime_devdeps_ok_eslint_9_fla

## Назначение
Добавить custom ESLint rule в orion-spec (v0.67+), который запрещает использование shell:true и синхронных execSync/spawnSync в production-коде. Цель — антирегрессия после B1 (CVE-class shell injection в orion run edit, закрыт в 84eff97). Контекст: - Проект: zero-dependency AI-agent toolkit, Node.js ≥22.12, ESM, "type": "module" - Стек: ESLint 9 flat config + typescript-eslint v8, см. eslint.config.js - B1 был: `spawnSync(editor, [scriptPath], { shell: true })` → исправлено через argv-match (editor.match(/\S+/g)) и shell:false - Текущие sync вызовы остались: 16 штук в src/core/docker.ts (execSync docker info/health), src/core/forgeConfig.ts (eslint --fix, prettier --write, gradlew spotlessApply), src/core/runtime.ts:718/729 (crontab -l / crontab - stdin для записи), src/cli/runCmd.ts (script watcher, repair), src/cli/commands/change.ts:250 и src/cli/commands.ts:305 (spawnSync для git check) - 3.8 shell-injection: основная работа сделана, остаётся страховка на будущее Задача: добавить ESLint rule(s), которые в `src/**/*.ts` (но не в тестах и не в examples/skills) выдают ERROR при: 1. `shell: true` в любом child_process вызове (spawnSync, execSync, spawn, exec, execFile, execFileSync) 2. Прямом использовании `execSync` / `spawnSync` (синхронные = блокируют Event Loop) Правила должны: - Работать через typescript-eslint flat config extension (или минимальный custom rule через @typescript-eslint/utils) - Иметь авто-фикс только где безопасен (предлагать замену execSync→execFile, spawnSync→spawn) - Допускать исключения через `// eslint-disable-next-line` с обязательным комментарием-обоснованием - Не ломать существующий код: правила WARN на первом этапе, переводятся в ERROR после того как все sync вызовы будут или удалены, или помечены обоснованием Шаги реализации (план): 1. Создать src/eslint-rules/ с custom rule (no-shell-true, no-sync-child-process) 2. Подключить в eslint.config.js как plugin 3. Прогнать lint, посмотреть violations → для каждого violation либо fix, либо disable с обоснованием (особенно для crontab/docker info — там sync оправдан) 4. Тесты для правил (unit-тесты на AST fixtures) 5. Добавить в CI (pnpm run lint уже есть) 6. Документация в CONTRIBUTING.md (раздел Security → Custom rules) Метрики успеха: - shell:true → 0 violations в src/ - execSync/spawnSync → 0 violations в src/ без обоснования; ≤4 обоснованных исключений (docker info, crontab, forgeConfig spotlessApply/fix, git check — это все легитимные sync) - Линт проходит в CI - Тесты для правил (≥6 кейсов на каждое правило) Constraints: - Не добавлять runtime dependencies (проект zero-dep) - devDeps typescript-eslint уже есть - Минимальный scope: один файл правила + подключение в конфиге + тесты - Совместимость с ESLint 9 flat config - Совместимость с typescript-eslint v8 Это антирегрессионная защита уже исправленного бага, не превентивная полировка — signal-driven. — node.js ESM CLI toolkit, Node ≥22.12, ESLint 9 flat config
