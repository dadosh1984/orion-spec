## 1. gsd-core — «Git. Ship. Done.»

**Что это:** фреймворк spec-driven разработки для AI-агентов (Claude Code,
Codex, Cursor, …). Фазовый цикл милстоуна: **Discuss → Plan → Execute → Verify → Ship**.
Вся тяжёлая работа (исследование, планирование, исполнение) выполняется
субагентами в свежих 200k-контекстах, чтобы главная сессия не «гнила»
(context rot).

**Сильные стороны:**
- **Субагентная оркестрация** — 37 субагентов (`agents/*.md`): planner, executor,
  verifier, code-reviewer, security-auditor…; исполнение параллельными волнами.
- **Память и обучение**: `mempalace-capture/recall` (запись решений в
  knowledge-graph), `extract-learnings` (уроки из завершённых фаз в LEARNINGS.md),
  `pattern-mapper`, `assumption-delta`, `gap-analysis`.
- **Верификация**: `verify-work` (конверсационный UAT), `schema-gate`, `drift`,
  `security` — отдельные гейты, а не обещания.
- **Охват рантаймов**: 45+ capability (claude, codex, copilot, cursor, opencode,
  pi, qwen, ollama, llama-cpp…).

**Слабые стороны:**
- **Сложность**: 75+ команд — крутой порог входа; «пакет вселенной», а не инструмент.
- **Тяжесть**: зависит от `@anthropic-ai/claude-agent-sdk` и `ws`; prompt-heavy
  (маркдаун-команды инжектятся в контекст — сами честно пишут «STOP: не читай
  этот файл, это тратит токены»).
- **Не детерминирован**: гейты — это промпты, а не исполняемые проверки; модель
  может не следовать.
- **Нет экономии токенов** — наоборот, большие промпты команд съедают контекст.

**Эффективность:** высокая на длинных автономных милстоунах (свежие контексты),
низкая на мелких задачах (оверхед команд и субагентов).
**Работоспособность:** сильная методология, но полагается на дисциплину модели.
**Польза пользователю:** высокая для больших проектов с автономным режимом;
оверкилл для мелких правок.

## 2. superpowers — методология из навыков

**Что это:** полная методология разработки для агента: **сначала дизайн, потом код**.
Навыки авто-триггерятся: brainstorming (HARD-GATE — никакого кода без одобренного
дизайна), writing-plans, executing-plans, subagent-driven-development, настоящий
красно-зелёный TDD, YAGNI/DRY, systematic-debugging, git-worktrees, code-review,
**verification-before-completion**.

**Сильные стороны:**
- **Дисциплина процесса**: Iron Law «NO COMPLETION CLAIMS WITHOUT FRESH
  VERIFICATION EVIDENCE» — ровно наш тезис честности, доведённый до правила.
- **Авто-триггеры**: навыки срабатывают сами, пользователю ничего не надо.
- **Субагентная разработка**: агенты работают по задачам плана часами автономно.
- **Один и тот же набор** работает в Claude Code, Codex, Cursor, Gemini, **Pi** и др.

**Слабые стороны:**
- **Ноль детерминизма**: всё — промпты; нет CLI, нет исполняемых гейтов, нет
  метрик/токен-учёта. Модель может проигнорировать навык.
- **Установка на каждый харнесс отдельно** (per-harness installation).
- **Нет экономии токенов**; полный набор навыков — заметный оверхед контекста.

**Эффективность:** средняя (методологическая, не техническая).
**Работоспособность:** хорошая там, где модель послушна; не проверяемо.
**Польза пользователю:** высокая для «поведенческого» улучшения агента; ничего
не даёт в плане верификации и экономии.

## 3. OpenSpec — spec-фреймворк

**Что это:** изменения (changes) с артефактами **proposal → specs → design → tasks →
implement** и дельта-спеками. CLI на TypeScript: `init`, `propose`, `new`,
`continue`, `ff`, `update`, `sync`, `archive`, `verify`, `validate`, `show`,
`doctor`, `workset`, `explore`… Новый воркфлоу **OPSX** сделал инструкции
редактируемыми (schema.yaml + templates/*.md) — без релиза, с мгновенным эффектом.

**Сильные стороны:**
- **Зрелая артефактная модель**: proposal/specs/design/tasks, дельта-спеки,
  `validate`, `archive`, миграции, worksets, конфиг проекта с инжекцией контекста.
- **OPSX — открытость**: «hardcoded prompts → user-editable templates» — любой
  может править промпты и пробовать без ожидания релиза.
- **Детерминированный CLI** (в отличие от чисто-промптовых конкурентов).

**Слабые стороны:**
- **Нет цикла исполнения**: design→tasks передаются агенту вручную; нет
  TDD-движка, нет гейтов lint/type/test в самом инструменте (есть только `verify`).
- **Нет экономии токенов** и анализа стоимости.
- **Только спеки** — не компаньон, а библиотека артефактов.

**Эффективность:** детерминированная, но без cost-awareness.
**Работоспособность:** высокая для процесса, средняя для проверки результата.
**Польза пользователю:** сильная для организационной spec-дисциплины; наш
think→draft — та же модель артефактов, что подтверждает правильность выбора.

## 4. spec-kit (GitHub) — spec-driven + расширения

**Что это:** тулкит «define what to build before building it»: Python CLI
`specify` (init/bundle/extension/integration/preset), бандлы по ролям,
**полноценная система расширений** (новые команды, шаблоны, фазы),
каталог сообщества, интеграции с агентами.

**Сильные стороны:**
- **Экосистема расширений**: extensions с API, каталог community, ролевые
  бандлы, пресеты — «make it yours» (как плагины, но зрелее).
- **Фазы как объекты**: расширения могут добавлять целые новые фазы процесса.
- Официальный проект GitHub, документация на GitHub Pages.

**Слабые стороны:**
- **Python-зависимость** — не zero-dep, противоположность нашему принципу.
- **Нет исполнения/гейтов**: только спецификации + генерация; верификация и
  экономия токенов не входят.
- Нет встроенной памяти/обучения.

**Эффективность:** средняя; **Работоспособность:** CLI детерминирован;
**Польза:** организационная стандартизация спецификаций, каталог расширений.

## 5. rtk — Rust Token Killer (уже изучен нами в v0.11)

**Что это:** одиночный Rust-бинарник-прокси: перехватывает bash-вывод и сжимает
до −90% токенов перед чтением LLM. 100+ поддерживаемых команд (14 модулей:
git/js/python/go/rust/…), оверхед <10 мс. Хуки для каждого агента (claude,
codex, opencode, cursor, **pi**, antigravity…). `rtk gain` — учёт токенов
(bytes/4), `rtk learn` — **детекция повторяющихся CLI-ошибок из JSONL-сессий
Claude** и автогенерация правил (`.claude/rules/cli-corrections.md`),
таксономия ErrorType + дедупликация CorrectionRule с confidence.

**Сильные стороны:**
- **Производительность**: Rust, <10 мс, −90%.
- **Широта**: 100+ команд сжатия.
- **`learn`**: самообучающиеся правила исправления ошибок из истории сессий —
  самая близкая к нашей v0.12 идея (но у них — для CLI-команд, у нас — для
  воркфлоу-шагов).
- **`gain`**: честные bytes/4 оценки (мы это же сделали в v0.11).

**Слабые стороны:**
- **Одноцелевой**: только сжатие вывода; нет воркфлоу/спек/верификации.
- Требует установки прокси/хука на каждый агент; `learn` завязан на сессии
  Claude (не агент-агностичен).

**Эффективность:** лучшая в своей нише. **Работоспособность:** высокая,
fail-safe. **Польза:** прямая экономия токенов любому агенту.

## 6. ponytail — «ленивый сеньор»

**Что это:** скилл/хук-система, заставляющая агента писать минимальный код:
YAGNI → стандартная библиотека → одна строка. Режимы lite/full/ultra; хуки
runtime (принуждение режима), subagent (делегирование), statusline; команды
`ponytail`, `ponytail-audit`, `ponytail-debt`, **`ponytail-gain`** (учёт
экономии), `ponytail-review`. Работает с 20 агентами.

**Сильные стороны:**
- **Честные бенчмарки**: ≈−54% кода (до 94%), −20% стоимость, −27% время,
  100% safe; сами честно пишут «per-task ceiling, not average» — образцовая
  честность измерений (ровно наш принцип «no fake savings»).
- **Механизм режимов** (интенсивность скилла) и **audit/debt** (долг и аудит
  упрощений).
- **gain** — учёт экономии, как наш economy ledger.

**Слабые стороны:**
- Промпт/скилл-основа: модель может не следовать; нет детерминированной
  проверки «код минимален».
- Одна идея (минимализм), нет спека/гейтов/памяти.

**Эффективность:** хорошая (меньше кода → меньше токенов на diff/чтение).
**Работоспособность:** средняя (промпты). **Польза:** реальное сокращение кода
и стоимости при дисциплинированной модели.

## 7. orion-spec (наш) — сводка по фактам

- **Ноль зависимостей** (TypeScript, без runtime-пакетов), пакет 147 КБ,
  CLI + MCP-сервер **stdio, 16 инструментов** — агент-агностичен (35+ моделей).
- **Воркфлоу**: think → draft (proposal/specs/design/tasks, `[fact]`/`[assumption]`)
  → forge (**настоящий TDD-движок** RED-GREEN-REFACTOR, генерит тесты и гоняет
  vitest) → shield (lint/type/test/**drift**/security гейты + свежесть по
  context-hash) → out (вердикт SUCCESS/INCOMPLETE по контексту).
- **Экономия токенов** (v0.11): собственный компрессор (9 детерминированных
  правил, fail-safe, «no fake savings», RU/EN-безопасное усечение), кэш по хэшу,
  ledger `~/.orion/economy.json` по проектам, cost-aware `next` (cheapest-first),
  метрики с ASCII-графиками.
- **Самокоррекция и обучение** (v0.12): уроки `~/.orion/lessons.json`,
  автозахват ошибок shield/out/forge, `next` возвращает в `think` с исправленной
  задачей, `think` прикрепляет `appliesLessons` — обучение между проектами;
  `track lessons`, MCP `lessons_list`.
- 255 тестов, покрытие 89.88%, CI зелёный; плагины, `serve` (веб-дашборд),
  Docker-песочница, YAGNI-лестница (`scale`).

**Честные слабые стороны (чтобы не хвалить себя):**
- Один разработчик, крошечное сообщество; нет субагентной оркестрации и
  параллельных волн исполнения.
- Нет анализа истории сессий (rtk `learn` умеет; мы — только шаги воркфлоу).
- Промпты/шаблоны draft зашиты в TS — пользователь не может править без релиза
  (OpenSpec OPSX умеет).
- Компрессор: 9 правил против 100+ у rtk; нет хуков на каждый агент.
- Нет конверсационного UAT (gsd `verify-work`), нет memory-палас/knowledge-graph,
  нет ролевых бандлов (spec-kit).

## Что берём в orion-spec (идеи → улучшения, без копирования)

Приоритет по «ценность/стоимость» для нас (ноль зависимостей, агент-агностично,
честность):

### A. «Уроки из сессий» (идея rtk `learn`, улучшаем)
rtk учится на JSONL-сессиях Claude. Мы сделаем лучше: Orion читает **любые**
JSONL-сессии (у нас уже есть формат pi-сессий; MCP-агенты — свои), детектит
повторяющиеся ошибки (команда упала → исправлена) и **пишет их в наш
`lessons.json`** — тот самый, что кормит `next`/`think`. Итог: self-correction
начинает работать не только по шагам воркфлоу, но и по реальной истории
взаимодействия; агент-агностично (rtk — только Claude).

### B. «Редактируемые шаблоны» (идея OpenSpec OPSX, улучшаем)
OPSX правит промпты через schema.yaml+templates. Мы сделаем лучше: шаблоны
draft/think выносим в данные с fallback на встроенные:
`~/.orion/templates/*.md` + переопределение на уровень изменения
(`changes/<id>/templates/`). Без релиза, с мгновенным эффектом, плюс честная
маркировка «tweaked» в артефактах (чтобы не выдавать кастом за стандарт).

### C. «Learnings в out» (идея gsd `extract-learnings`, улучшаем)
gsd вытаскивает уроки из фаз. Мы сделаем лучше: `out` при SUCCESS автоматически
собирает в result.md секцию **«Уроки и решения»** из lessons.json этого изменения
+ список решений из proposal/draft — структурированно и связано с нашим store
(у gsd это отдельный LEARNINGS.md без связи с правилами).

### D. «Широта компрессора» (идея rtk 100+ команд, улучшаем)
Не копируем 100 правил — добавляем ~5–10 высокоценных детерминированных:
`docker`, `go test`, `pytest`, `cargo`, `terraform plan`, `psql` — с нашими
инвариантами (no fake savings, fail-safe, RU/EN-усечение).

### E. «YAGNI-аудит» (идея ponytail, улучшаем)
ponytail — промпты. Мы сделаем детерминированно: новый честный чек в `shield` —
**`yagni`**: для новых сниппетов изменения считает LOC/импорты/декларации и
помечает подозрительный over-engineering (без запрета — только сигнал), плюс
в `out` — строка «минимальность» (как `matched=false` у компрессора: нет
претензий, если нечего проверять).

### F. «Экономика сессии» (идея rtk `gain`/ccusage, улучшаем)
rtk считает токены команд. Мы добавим в `metrics` режим
`--session <file.jsonl>`: разбивка по ролям (thinking/tool/assistant/user) с
честной пометкой «≈ bytes/4 estimate» — ровно то измерение, что мы делали руками
в прошлой сессии, теперь встроено.

### G. (на будущее) «Субагентные волны» (идея superpowers/gsd)
Детерминированная версия: `forge` запускает независимые задачи параллельно в
отдельных процессах (у нас уже изоляция per-task в TDD-движке) с общим
guard-report — без SDK, только child_process.

## Вывод

- **Мы сильны там, где другие промптят**: исполняемые гейты, TDD-движок,
  экономия токенов с честным учётом, самокоррекция — уникальная комбинация
  (никто из шести не имеет всех трёх).
- **Догоняем в**: обучении на истории сессий (A), открытости шаблонов (B),
  выносе уроков в результат (C), широте сжатия (D), минимализме (E),
  аналитике сессий (F).
- **Не берём**: SDK-зависимости (gsd), Python (spec-kit), чисто-промптовые
  механизмы (superpowers/ponytail) — противоречат принципам zero-dep и честности.
- Рекомендуемый план: **v0.13 = A+B (обучение из сессий + редактируемые
  шаблоны)**, затем C+D (learnings в out + широта компрессора), затем E+F.
