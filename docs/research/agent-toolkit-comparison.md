## 1. gsd-core 1.9.1 — «Git. Ship. Done.»

**Что нового с прошлого среза:** самое активное развитие из шести (релизы
1.9.0/1.9.1 с двумя дюжинами PR за месяц). Ключевое:

- **Калибровка оценок по факту** (`estimate-check` / `estimate-calibration`,
  smart-zone budget): план оценивается в токенах, исполнитель записывает
  фактическую стоимость в SUMMARY.md, `/gsd:extract-learnings` считает
  поправку «оценка → факт» и будущие оценки само-калибруются. Превышение
  бюджетной зоны → advisory-флаг с рекомендацией разбить фазу.
- **Reviewer lanes как данные**: внешние кросс-ревьюверы (Claude, Codex,
  CodeRabbit, Gemini, …) объявлены в capability-манифестах, инсталляция
  раскрывает и требует согласия на отправку плана наружу.
- **Параллельные волны на не-Claude рантаймах**: изоляция исполнителей
  теперь «договорная способность» (worktree-изоляция, которую GSD создаёт и
  мержит сам, где харнесс не умеет).
- **verify-summary усилен**: заявленные в SUMMARY файлы проверяются на диске
  при завершении фазы; упоминания в прозе больше не считаются файлами.
- 34 субагента, capability-реестр с валидацией, `regen:derived` одной командой.

**Сильные стороны:** зрелость оркестрации; единственный из шести, кто
**измеряет фактические затраты и калибрует по ним планы**; гейты
верификации-существуют-файлы; честность согласия на отправку данных наружу.

**Слабые стороны:** по-прежнему тяжёлый (SDK + ws + десятки команд, порог
входа высокий); гейты — во многом промпты; нет экономии токенов в сессии
(наоборот — большие промпты); Windows-проблемы решаются точечно (что видно
по changelog).

**Эффективность:** высокая на длинных автономных милстоунах, оверхед на
мелких задачах. **Работоспособность:** сильная методология, много кода —
и много же мест, где «модель может не послушаться». **Польза:** высокая для
команд с большими проектами; оверкилл для одного разработчика.

## 2. superpowers 6.2.0 — методология из навыков

**Что нового:** v6.2.0 (июль) — subagent-driven development (закрытие
ревью-замечаний против живых eval-кампаний), кампания по сжатию промптов
навыков (убраны «recap» и продающие абзацы — каждый замерен субагентными

Gemini CLI.

**Сильные стороны:** дисциплина (Iron Law «NO COMPLETION CLAIMS WITHOUT FRESH
VERIFICATION EVIDENCE»); авто-триггеры навыков; 14 навыков покрывают
brainstorming → планы → SDD → TDD → code-review → verification; работает
в нескольких харнессах; умеют **сжимать собственные промпты с измерением
поведения** — это честный подход к размеру контекста, редкий в этой нише.

**Слабые стороны:** по-прежнему ноль детерминизма: всё — промпты, нет CLI,

отдельно; скиллы — это поведение, а не проверяемый результат.

**Эффективность:** средняя (методологическая). **Работоспособность:** зависит
от послушности модели, не проверяемо. **Польза:** отличная как «тренинг
поведения» агента; не даёт верификации, экономии, измерений.

## 3. OpenSpec 1.8.0 — spec-фреймворк

**Что нового:** 1.8.0 (август): vendor-neutral таргет `.agents/skills/`
(AGENTS.md-совместимые ассистенты); новые таргеты (Rovo, Copilot cloud,

может при архивировании удалить main spec); единый парсер tasks.md для
прогресса и apply (считает вложенные подзадачи); `validate` предупреждает о
потере сценариев MODIFIED; конфликт-подсказки для агентов с закрытым stdin.

**Сильные стороны:** самая зрелая артефактная модель; OPSX (редактируемые
шаблоны); честные статусы; безопасный retire; ориентация на агентов с
закрытым stdin (pasteable флаги) — редкое внимание к UX для агентов.

**Слабые стороны:** нет цикла исполнения (нет TDD-движка, нет гейтов
lint/type/test — есть только `verify`/`validate`); нет экономии токенов;
спеки — библиотека артефактов, не компаньон.

**Эффективность:** детерминированная, без cost-awareness. **Работоспособность:**
высокая для процесса. **Польза:** сильная для spec-дисциплины команд.

единственный из шести, кто делает «отложенное упрощение» проверяемым;

## 7. orion-spec 0.17.0 — сводка по фактам

- **Ноль зависимостей**, пакет ~147 КБ; CLI + **MCP-сервер stdio (17 тулов)**
  — агент-агностичен (любой MCP-клиент: Claude Code, Codex, opencode,
  Cursor, Cline, …).
- **Воркфлоу**: think → draft (proposal/specs/design/tasks) → forge
  (**настоящий TDD-движок** RED-GREEN-REFACTOR + параллельные волны через
  `fork`, v0.16) → shield (**7 детерминированных гейтов**: lint, type, test,
  drift, yagni, **economy**, security; WARN-сигналы никогда не блокируют) →
  out (честный вердикт + уроки).
- **Экономия токенов**: собственный компрессор (18 детерминированных правил,
  fail-safe, «no fake savings», ledger `~/.orion/economy.json` — сейчас
  ≈128 К tok / 152 операций), кэш по хэшу, cost-aware `next` (cheapest-first),
  **economy-шаг в shield** и **футер экономики в `next`** (v0.17) — экономика
  теперь видна там, где принимаются решения.
- **Самокоррекция и обучение**: уроки `~/.orion/lessons.json`, автозахват
  ошибок, `orion learn` читает любые JSONL-сессии, `next` возвращает в `think`,
  уроки попадают в `out`.
- **Открытость**: редактируемые шаблоны (v0.13), плагины, `serve` (веб-дашборд).
- 325 тестов, покрытие 91.68%, CI зелёный.

**Честные слабые стороны:**
- Один разработчик; нет конверсационного UAT (gsd `verify-work`), нет
  кросс-ревьюверов (gsd reviewer lanes), нет ролевых бандлов (spec-kit).
- Наши оценки стоимости («~N tok» в `next`) **не калибруются по факту** —
  gsd это уже делает; это наш главный пробел в экономике.
- Нет реестра отсроченного долга (ponytail `debt`) — YAGNI-WARN даёт сигнал,
  но «потом» нигде не фиксируется.
- Нет явного «retire capability» (OpenSpec) — манифесты дрейфа только растут.
- Нет «planning vs implementation» статуса, отдельного от фазы (OpenSpec
  `status`) — у нас фазы в `next` уже это дают, но без единого честного среза.

## Что берём в orion-spec: план v0.18 (идеи → улучшения, без копирования)

Из A–G прошлого плана всё закрыто. Новый шорт-лист по «ценность/стоимость»,
с сохранением принципов (zero-dep, честность, WARN не блокирует, без новых
CLI-команд):

### H. Калибровка оценок по факту (идея gsd estimate-calibration → улучшаем)
gsd калибрует оценки фаз по SUMMARY.md (исполнитель сам пишет фактическую
стоимость — субъективно). Мы сделаем детерминированно и честно: при `out`
SUCCESS фактический вес изменения = суммарный размер файлов изменения в
байтах ÷ 4 (наш честный «≈ bytes/4») пишется в `~/.orion/calibration.json`
вместе с оценкой, которую давал `next`. При следующем `next` — коэффициент
поправки (медиана факт/оценка по истории ≥3 изменений): строка
`≈ N tok (калибровано ×0.8 по 5 изменениям)` или честное `(не калибровано)`
при отсутствии истории. Никакой телеметрии, всё локально, всё честно.

### I. Реестр отсроченного долга (идея ponytail-debt → улучшаем)
ponytail собирает `ponytail:`-маркеры вручную. Мы сделаем автоматически и
честно: когда shield выдаёт YAGNI-WARN по сниппету — запись в
`~/.orion/debt.json` (путь сниппета, LOC vs медиана, дата). Когда изменение
завершается и сниппет больше не триггерит WARN — запись автоматически
закрывается. `next` показывает счётчик открытых долгов в футере;
`track status` — их список. «Later» становится проверяемым, а не «never»;
долг создаётся только реальным сигналом (WARN), а не обещанием.

### J. Бюджетная зона в `next` (идея gsd smart-zone → улучшаем)
proposal уже несёт `budget`. Если калиброванная оценка кандидата превышает
бюджет изменения — честный WARN в строке кандидата:
`превышает бюджет ~N tok — рассмотрите разбивку` (advisory, не блок).

### K. (на будущее) Честный срез «planning vs implementation» (идея OpenSpec `status`)
У нас фазы уже различают это, но можно добавить в `next`/`track status`
однострочный статус изменения: `planning complete, 2/4 tasks done,
guard PASS` — без новых команд.

### Не берём (с обоснованием)
- Кросс-ревьюверы gsd — требуют отправки данных наружу и SDK; противоречит
  zero-dep и приватности (наша security-проверка — локальная и бесплатная).
- Python (spec-kit), хуки на каждый харнесс (rtk/gsd) — против zero-dep и
  агент-агностичности (наш MCP покрывает всех одним сервером).
- Чисто-промптовые механизмы (superpowers/ponytail) — как есть, без
  детерминированной проверки они не вписываются в нашу модель честности.
- Retire capability (OpenSpec) — у нас манифесты дрейфа растут осознанно;
  механика удаления появится, если появится реальный сценарий удаления.

## Вывод

- **Мы по-прежнему уникальны по комбинации**: исполняемые гейты + TDD-движок
  + честная экономия токенов + самокоррекция + MCP для всех агентов.
- **Главный пробел, найденный обновлённым сравнением**: оценки стоимости не
  сверяются с реальностью (gsd это делает) и «отложенное упрощение» нигде не
  фиксируется (ponytail это делает). Оба пункта — ровно в духе нашей честной
  экономики.
- **Рекомендуемый следующий инкремент: v0.18 = H + I + J** (калибровка оценок,
  реестр долга, бюджетная зона) — три небольших честных фичи, все без новых
  CLI-команд, все в существующих конвейерах (next/shield/out/track status).
