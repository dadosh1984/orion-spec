# План реализации улучшений для проекта Orion

## Этап 1: Модернизация технологий - замена PowerShell-скриптов на кроссплатформенные Node.js альтернативы

**Описание:** Заменить все PowerShell-зависимые вызовы в скриптах проекта на эквивалентные реализации utilizzando только встроенные модули Node.js (fs, child_process, path) для обеспечения истинной кроссплатформенной совместимости в скрипте `scripts/install-git-hooks.js` и других вспомогательных скриптах.

**Необходимые ресурсы:**
- Инструменты: Node.js v22.12+, модули fs, child_process, path (уже в проекте)
- Специалисты: 1 разработчик с опытом кроссплатформенной Node.js разработки
- Данные: текущее содержимое `scripts/install-git-hooks.js`, требования к поведению хуков Git
- Файлы для модификации: `scripts/install-git-hooks.js`, потенциально другие скрипты в директории `scripts/`

**Ожидаемые результаты (KPI):**
- Удаление всех вызовов `powershell.exe` или `powershell` из скриптов проекта
- 100% успешное выполнение `npm run hooks:install` на Windows, Linux и macOS в CI
- Отсутствие ошибок "command not found" связанных с PowerShell в логах сборки
- Сохранение идентичного поведения создания и модификации git-hook файлов на всех платформах

**Анализ рисков:**
- Риск: Изменение поведения при работе с путями содержащими пробелы или специальные символы
  Минимизация: Использовать `child_process.spawn` с массивом аргументов и `shell: false`, тестировать с разнообразными именами файлов
- Риск: Потенциальная несовместимость для пользователей с кастомными PowerShell-зависимыми workflows
  Минимизация: Сохранить тот же интерфейс CLI и ожидаемый результат скрипта, добавить обратную совместимость через параметры если необходимо
- Риск: Увеличение сложности кода из-за необходимости обработки кроссплатформенных различий вручную
  Минимизация: Использовать кроссплатформенныеNode.js API (например, `path.sep` вместо жестких разделителей), избегать платформо-специфичных условий где возможно

## Этап 2: Оптимизация производительности - ленивая загрузка тяжелых зависимостей

**Описание:** Обеспечить ленивую загрузку Playwright и других тяжелых зависимостей только при фактической необходимости (когда установлена переменная окружения `ORION_SANDBOX=browser`), переместив динамические импорты из верхнего уровня модулей внутрь функций их использующих.

**Необходимые ресурсы:**
- Инструменты: существующая кодовая база, TypeScript компилятор
- Специалисты: 1 разработчик熟悉 с динамическими импортами в TypeScript и оптимизацией запуска
- Данные: текущее содержимое `src/core/browser.ts` и других файлов импортирующих Playwright
- Файлы для модификации: `src/core/browser.ts`, потенциально другие файлы с импортами Playwright

**Ожидаемые результаты (KPI):**
- Сокращение времени холодного старта CLI на 200-500мс для пользователей не использующих браузерную песочницу
- Сокращение базового потребления памяти на 10-15МБ в состоянии простоя
- Отсутствие ошибок при попытке импортировать Playwright в средах где он не установлен (при `ORION_SANDBOX!==browser`)
- Сохранение полной функциональности браузерной песочницы при `ORION_SANDBOX=browser`

**Анализ рисков:**
- Риск: Увеличение сложности отладки из-за асинхронной природы динамических импортов
  Минимизация: Добавить четкую обработку ошибок и логирование при неудачной загрузке Playwright
- Риск: Потенциальные гонки состояния если несколько частей кода пытаются загрузить Playwright одновременно
  Минимизация: Реализовать кэширование результата динамического импорта через замыкание или singleton pattern
- Риск: Неправильная работа при условной установке переменной окружения после первого импорта
  Минимизация: Проверить значение `ORION_SANDBOX` непосредственно перед каждой попыткой загрузки, а не кэшировать результат на основе первого проверки

## Этап 3: Повышение функциональной ценности - встроенный поиск и установка навыков

**Описание:** Добавить новые подкоманды `orion skill search <запрос>` и `orion skill install <имя>` для обнаружения и установки community-навыков из centralized реестра (начальная реализация через поиск по GitHub с фильтрацией по топику `orion-skill`).

**Необходимые ресурсы:**
- Инструменты: Node.js fetch API или аналогичный для HTTP-запросов, существующая система плагинов Orion
- Специалисты: 1-2 разработчика с опытом работы с GitHub API и CLI инструментами
- Данные: структура репозиториев с навыками в GitHub, текущая система загрузки навыков через `browser.ts`
- Файлы для создания: `src/cli/skills/`, `src/core/skillRegistry.ts`, модификация `src/cli/bootstrap.ts` для регистрации новых команд

**Ожидаемые результаты (KPI)::**
- Возможность поиска навыков по ключевым словам с возвратом релевантных результатов за <2 секунд
- Успешная установка навыка за <10 секунд при среднем сетевом соединении
- Автоматическое обнаружение и загрузка установленных навыков при последующих вызовах `orion run <навык>`
- Снижение барьера входа для новых пользователей: измерение времени от первого запуска `orion` до выполнения первого навыка снизится на 50%+

**Анализ рисков:**
- Риск: Зависимость от внешних сервисов (GitHub) и их ограничения по rate limiting
  Минимизация: Реализовать локальное кэширование результатов поиска на 1 час, добавить fallback на локальный реестр
- Риск: Потенциальная небезопасность при автоматической загрузке и выполнении стороннего кода
  Минимизация: Ограничить загрузку только репозиториев с явным топиком `orion-skill`, показывать предупреждения перед установкой, запускать навыки в изолированном контексте
- Риск: Фрагментация экосистемы из-за множества неофициальных реестров навыков
  Минимизация: Начать с официального реестра Orion на GitHub, предоставить четкие руководства по публикации навыков

## Этап 4: Улучшение UX - интерактивная визуализация пайплайна

**Описание:** Добавить флаг `--visual` к команде `orion new` (и связанным командам pipeline) для вывода реального времени прогресса пайплайна `think → draft → forge → shield → out` в виде индикатора выполнения с этапами, статусами и ожидаемым временем оставшегося выполнения.

**Необходимые ресурсы:**
- Инструменты: существующая система событий и состояние изменений, библиотеки для ASCII/SVG прогресс-баров (например, `cli-progress` или кастомное решение)
- Специалисты: 1 разработчик с опытом построения интерактивных CLI интерфейсов
- Данные: текущая структура событий pipeline в `src/core/autopilot.ts` и `src/core/changeShield.ts`
- Файлы для модификации: `src/cli/newCmd.ts`, `src/core/pipelineVisualizer.ts` (новый файл), потенциально модификация событийной системы

**Ожидаемые результаты (KPI):**
- При использовании `--visual` пользователь видит четкий прогрессбар с этапами и текущим статусом
- Снижение количества повторных запросов пользователя о статусе длительных операций на 70%+
- Возможность отслеживания прогресса в головless режиме через перенаправление вывода в файл
- Сохранение обратной совместимости: отсутствие `--visual` не меняет поведения команды

**Анализ рисков:**
- Риск: Снижение производительности из-за избыточного логирования и рендеринга визуализации
  Минимизация: Обновлять визуализацию не чаще чем раз в 500мс, использовать буферизованный вывод
- Риск: Сложность в синхронизации визуализации с асинхронными этапами pipeline
  Минимизация: Привязать обновления визуализации к существующим событиям изменения состояния изменений
- Риск: Неудобство использования в очень узких терминалах или при перенаправлении вывода
  Минимизация: Добавить адаптивный режим который упрощает вывод при малой ширине терминала, сделать визуализацию полностью отключаемой через переменную окружения

## Этап 5: Рефакторинг кода - консолидация устаревших псевдонимов команд

**Описание:** Создать централизованную таблицу сопоставления устаревших псевдонимов команд и единый обработчик предупреждений в `src/cli/parse.ts`, удалив разбросанные проверки по всему кодобазе и упростив поддержку deprecated команд.

**Необходимые ресурсы:**
- Инструменты: существующая система парсинга аргументов, модуль для вывода цветных предупреждений
- Специалисты: 1 разработчик familiar with the CLI architecture and deprecation patterns
- Данные: список всех текущих deprecated aliases из `src/cli/parse.ts` и `commands.ts` (примерно 35 единиц)
- Файлы для модификации: `src/cli/parse.ts` (централизация), `src/cli/commands.ts` (удаление дублирующей логики), потенциально очистка старых проверок в обработчиках команд

**Ожидаемые результаты (KPI):**
- Сокращение количества строк кода связанных с обработкой deprecated aliases на 60%+
- Единый формат предупреждений о deprecated командах: `[WARNING] Deprecated alias 'old' used. Use 'new' instead.`
- Упрощение добавления новых deprecated aliases: достаточно добавить запись в централизованную таблицу
- Сохранение полной обратной совместимости: все старые команды продолжают работать с предупреждением
- Упрощение документации: одна страница с полным списком deprecated aliases и их заменами

**Анализ рисков:**
- Риск: Упущение некоторых deprecated aliases при миграции на централизованную систему
  Минимизация: Составить полный список через поиск по regex `DEPRECATED_ALIASES` и старым вызовам в legacy switch перед началом работ
- Риск: Изменение порядка или формата предупреждений который может сломать парсеры вывода
  Минимизация: Сохранить те же уровни логирования (stderr) и префиксы предупреждений, изменить только текст сообщения
- Риск: Сложность в отладке из-за дополнительного уровня абстракции
  Минимизация: Добавить юнит-тесты для новой системы обработки aliases, логировать внутренние переходы в режиме verbose

## Этап 6: Повышение функциональной ценности - добавление анализа влияния изменений

**Описание:** Добавить флаги `--dry-run` и `--analyze` к командам `orion forge` и `orion shield` для предварительного анализа потенциального влияния выполнения операций на кодовую базу без реальных модификаций, включая список затрагиваемых файлов, оценку времени выполнения и предупреждения о потенциально breaking changes.

**Необходимые ресурсы:**
- Инструменты: существующая система отслеживания файлов в изменениях, модули для статического анализа зависимостей (например, `madge` или кастомное решение)
- Специалисты: 1-2 разработчика с опытом в анализе влияния изменений и static analysis
- Данные: текущая структура task файлов в `changes/<id>/tasks.md`, система выполнения операций в `src/core/autopilot.ts`
- Файлы для модификации: `src/cli/forgeCmd.ts`, `src/cli/shieldCmd.ts`, `src/core/changeAnalyzer.ts` (новый файл), потенциально модификация `src/core/runtime.ts` для сухого выполнения

**Ожидаемые результаты (KPI):**
- Возможность выполнить `orion forge <id> --dry-run` и получить детальный отчет за <5 секунд
- Отчет включает: список файлов которые будут изменены, созданы или удалены, оценку времени выполнения, предупреждения о потенциально breaking changes
- Снижение количества неудачных попыток `forge` из-за непредвиденных последствий на 40%+
- Повышение уверенности пользователей при выполнении потенциально опасных операций (например, refactoring core модулей)
- Сохранение возможности точного сухого выполнения через изоляцию файловой системы в памяти или временной директории

**Анализ рисков:**
- Риск: Невозможность точно предсказать все side-effects без реального выполнения (например, зависимость от runtime state)
  Минимизация: Четко помечать анализ как "потенциальное влияние" и рекомендовать реальное выполнение в изолированной среде для критических операций
- Риск: Увеличение времени выполнения команды из-за дополнительного анализа
  Минимизация: Делать анализ опциональным по флагу, кэшировать результаты анализов для неизменных кодов баз
- Риск: Ложные срабатывания системы анализа приводящие к излишней тревоге пользователей
  Минимизация: Сфокусироваться на высоковероятных проблемах (изменение публичных API, удаление файлов), использовать существующие типы и линтеры для базового анализа

## Этап 7: Улучшение архитектуры - внедрение плагинной системы валидаторов

**Описание:** Рефакторинг системы `orion shield` для использования плагинной архитектуры где каждый этап валидации (lint, type-check, tests, drift-check и т.д.) реализуется как отдельный плагин со стандартным интерфейсом, позволяя сообществу раславять функциональность shield без модификации ядра.

**Необходимые ресурсы:**
- Инструменты: существующая система shield в `src/core/shield/`, модульная архитектура TypeScript
- Специалисты: 1-2 архитектора с опытом в дизайне плагинных систем и dependency injection
- Данные: текущая реализация этапов shield в `src/core/shield/adapter.ts` и связанных файлах
- Файлы для создания: `src/core/shield/validatorInterface.ts`, `src/core/shield/pluginManager.ts`, модификация существующих валидаторов для соответствия интерфейсу
- Файлы для модификации: `src/core/shield/adapter.ts` (преобразование в плагинный менеджер), `src/core/changeShield.ts` (интеграция с новой системой)

**Ожидаемые результаты (KPI):**
- Возможность добавления нового этапа валидации через простой вызов `orion shield plugin install <validator-name>` без пересборки ядра
- Сокращение времени добавления нового типа проверки с часов/дней до минут
- Стандартный интерфейс для валидаторов: `{ name: string; validate: (context: ShieldContext) => Promise<ValidationResult>; }`
- Сохранение обратной совместимости: все существующие этапы shield продолжают работать как встроенные плагины
- Возможность конфигурирования порядка выполнения и включения/выключения этапов через конфигурационный файл

**Анализ рисков:**
- Риск: Снижение производительности из-за дополнительного слоя абстракции и динамической загрузки плагинов
  Минимизация: Кешировать разрешенные плагины, использовать синхронную загрузку где возможно, benchmarkть критические пути
- Риск: Сложность в обеспечении типа безопасности при динамической загрузке плагинов
  Минимизация: Использовать TypeScript с declaration files для плагинов, требовать экспорта типизированных функций
- Риск: Потенциальные конфликты между плагинами модифицирующими одни и те же аспекты кода
  Минимизация: Определить четкие фазы валидации (pre-lint, lint, post-lint и т.д.) с строгим порядком выполнения внутри фазы

## Этап 8: Повышение качества разработки - улучшение ясности сообщений об ошибках

**Описание:** Внедрить стандартную систему форматирования ошибок по всему кодобазу, которая предоставляет машинно-читаемый код ошибки, простое объяснение проблемы, конкретное предложенное решение и ссылку на соответствующую секцию документации.

**Необходимые ресурсы:**
- Инструменты: существующая система логирования, потенциально малая библиотека для форматирования ошибок (или кастомное решение)
- Специалисты: 1 разработчик с опытом в UX writing и дизайне ошибок
- Данные: текущие сообщения об ошибках в `src/core/hazards.ts`, `src/core/router.ts` и других критических местах
- Файлы для создания: `src/core/errorFormatter.ts`, `src/core/errorCodes.json` (или аналогичный справочник)
- Файлы для модификации: ключевые файлы где генерируются ошибки (оценка: 15-20 файлов)

**Ожидаемые результаты (KPI):**
- Все сообщения об ошибках следуют формату: `[ORION-ERR-XXXX] Описание проблемы\nРешение: Предложенное действие\nДокументация: ссылка`
- Снижение среднего времени решения типичных проблем пользователями на 30%+ (измеряется через опросы или анализ поддержки)
- Увеличение количества самопомощи пользователей: рост доли решений без обращения в поддержку на 25%
- Сохранение всей отладочной информации в режиме verbose или debug для разработчиков
- Возможность машинной обработки ошибок через парсинг кодов ошибок

**Анализ рисков:**
- Риск: Увеличение размера бинарного файла из-за включения строк документации и объяснений
  Минимизация: Хранить объяснения и ссылки в отдельном JSON файле, подгружать только при необходимости, использовать сжатие
- Риск: Сложность в поддержке актуальности ссылок на документацию при её изменении
  Минимизация: Хранить ссылки как относительные пути к документации в репозитории, проверять их действительность в pre-commit hook
- Риск: Изменение привычного формата ошибок который могут парсить внешние системы
  Минимизация: Сохранить машинно-читаемый префикс (например, ORION-ERR-) и структуру, оставить существующие системы парсинга работать через обновленные regex

## Этап 9: Модернизация конфигурации - добавление схемы валидации конфигурации

**Описание:** Внедрить валидацию JSON-схемы для файлов конфигурации `.orionrc` и переменных окружения `ORION_*` используя библиотеку `ajv` или аналогичную, с четкими сообщениями об ошибках при неверной конфигурации и значениями по умолчанию для опциональных полей.

**Необходимые ресурсы:**
- Инструменты: библиотека `ajv` (добавить в devDependencies), существующая система загрузки конфигурации
- Специалисты: 1 разработчик с опытом в JSON-схемах и валидации входных данных

## Этап 10: Повышение функциональной ценности - добавление встроенного набора для бенчмаркинга

**Описание:** Расширить существующую команду `orion metrics` для включения стандартного набора измеряемых нагрузок (benchmark-сценариев) с возможностью сравнения текущей производительности против базовых показателей и исторических запусков, измеряя wall-clock time, использование памяти и количество операций.

**Необходимые ресурсы:**
- Инструменты: существующая система metrics, набор типовых задач для измерения (например, валидатор E.164 из AGENTS.md)
- Специалисты: 1-2 разработчика с опытом в построении benchmark систем и статистическом анализе
- Данные: текущая реализация `orion metrics` из `src/core/metrics.ts`, описание benchmark задач из сессии saves
- Файлы для модификации: `src/core/metrics.ts`, `src/core/benchmarkSuite.ts` (новый файл), потенциально добавление директории `benchmarks/`
- Данные для benchmark: набор стандартизированных входных данных для типовых задач (CSV для валидатора E.164 и т.д.)

**Ожидаемые результаты (KPI):**
- Возможность запустить `orion benchmark run standard` и получить детальный отчет с wall-clock time, использованием памяти, количеством операций для каждого сценария
- Сравнение результатов против базового уровня (например, main branch) с вычислением процентного улучшения/ухудшения
- Хранение результатов benchmarkов в `.orion/benchmark-history.json` для анализа трендов во времени
- Возможность выборочного запуска конкретных сценариев: `orion benchmark run e164-validator`
- Стандартизированный набор включает минимум 5 разнообразных сценариев охватывающих разные аспекты производительности (I/O, CPU, память, типичные пользовательские workflows)

**Анализ рисков:**
- Риск: Benchmark сценарии не представляют реальную нагрузку пользователей и приводят к ложным выводам
  Минимизация: Базировать сценарии на реальных пользовательских задачах из AGENTS.md сессий saves и обратной связи сообщества
- Риск: Внешние факторы (нагрузка системы, другие процессы) влияют на результаты benchmarkов
  Минимизация: Выполнять каждый сценарий múltiples veces и брать медиану, измерять в изолированной среде если возможно
- Риск: Потенциальное замедление разработки из-за обязательного прогона benchmarkов перед коммитом
  Минимизация: Сделать benchmark запуск опциональным по флагу, интегрировать в pre-commit hook только по желанию пользователя
- Риск: Сложность в поддержке актуальности benchmark сценариев по мере развития проекта
  Минимизация: Назначить ответственного за поддержку benchmark suite, включать обновления сценариев в процесс релиза при значительных изменениях ядра
